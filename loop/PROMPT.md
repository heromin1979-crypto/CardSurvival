# 작업 지시서

너는 이 저장소에서 한 바퀴를 도는 작업자다.
이전 바퀴와 대화가 이어지지 않는다. 네가 아는 것은 아래 문서에 적힌 것뿐이다.
그러므로 네가 남기지 않은 것은 다음 바퀴에게 존재하지 않는다.

---

## ① 합격 기준

**`docs/loop/INBOX.md` 의 "처리할 것"에 남은 지적이 0건이 되면 이번 라운드는 끝이다.**

시작할 때 이미 0건이면 만들 것이 없다는 뜻이다.
아무것도 만들지 말고, STATUS 를 건드리지 말고, 바퀴를 끝낸다.
할 일을 스스로 만들어내지 않는다.

---

## ② 먼저 읽을 문서

아래 순서대로 읽는다. 순서가 곧 우선순위다. 충돌하면 번호가 작은 쪽이 이긴다.

| 순서 | 문서 | 어디까지 읽을지 |
|------|------|-----------------|
| 1 | `docs/loop/INBOX.md` | "처리할 것" 절 전체 |
| 2 | `docs/loop/STATUS.md` | "다음에 할 것" 맨 위 1개 + "결정과 근거" 전체 + "막힌 것" 전체. **"끝난 것"은 읽지 않는다** |
| 3 | `docs/loop/SPEC.md` | 1~3절 항상. 4~7절은 이번 작업에 걸릴 때만 |
| 4 | `DESIGN.md` (저장소 루트) | Typography · Color · Spacing · Motion · Decisions Log |
| 5 | `css/variables.css` | 이번에 손댈 값의 토큰 이름 |

읽지 않은 문서를 근거로 판단하지 않는다.

4번과 5번은 이 브랜치가 UI 작업이라 넣었다.
루트 `DESIGN.md` 는 디자인 시스템이고, `docs/loop/SPEC.md` 는 이번 라운드 기획이다. 다른 파일이다.

`CLAUDE.md` 는 여기 적지 않는다. 세션이 시작할 때 자동으로 들어온다.
같은 이유로 거기 있는 규칙을 ③에 옮겨 적지 않는다 — 두 곳에 있으면 한쪽만 고쳐져 어긋난다.

## ③ 규칙과 근거

| 규칙 | 왜 |
|------|-----|
| INBOX 에 없는 것은 고치지 않는다. 눈에 띄면 INBOX 에 적고 두고 간다 | 미적 판단은 사람이 한다. 루프가 스스로 정하면 바퀴마다 취향이 달라져 서로 되돌린다 |
| `css/` 와 그 화면의 컴포넌트만 고친다. `js/systems/`, `js/data/` 는 건드리지 않는다 | 이번 라운드는 보이는 것의 문제다. 로직에 손대는 순간 회귀 범위가 게임 전체로 넓어진다 |
| `css/variables.css` 에 없는 색·간격·폰트를 새로 만들지 않는다. 필요하면 INBOX 에 남긴다 | 토큰 밖의 값이 늘면 디자인 시스템이 문서가 아니라 장식이 된다 |
| 파일을 지우거나 통째로 다시 쓰기 전에 STATUS "결정과 근거"에 이유를 먼저 적는다 | 다음 바퀴는 지워진 것을 볼 수 없다. 이유가 없으면 같은 것을 다시 만들거나 되살린다 |
| 같은 작업이 두 바퀴 연속 실패하면 STATUS "막힌 것"으로 올리고 다른 것을 한다 | 같은 벽에 계속 부딪히면 바퀴만 소모된다 |
| 옆 규칙의 작성 방식을 따른다. 더 나은 방식이 보여도 이번 바퀴에 바꾸지 않는다 | 스타일 변경이 섞이면 진짜 변경이 무엇인지 안 보인다 |
| `DESIGN.md` 의 Decisions Log 와 어긋나는 변경은 하지 않는다. 어긋나야 한다면 INBOX 에 먼저 묻는다 | 거기 적힌 것은 이미 사람이 이유를 달아 내린 결정이다. 모르고 뒤집으면 같은 논의를 반복한다 |

## ④ 한 바퀴 도는 순서

1. **읽기** — ②의 문서를 순서대로 읽는다.
   INBOX "처리할 것"의 맨 위 항목이 이번 바퀴의 작업이다.
   비어 있으면 STATUS "다음에 할 것" 맨 위 항목을 본다.
   **둘 다 비어 있으면 아무것도 하지 않고 바퀴를 끝낸다.**

2. **하나만 만들기** — 이번 바퀴에서는 한 가지만 한다.
   둘 이상 손대면 하나가 깨졌을 때 어느 쪽 때문인지 알 수 없다.

3. **실행해서 눈으로 확인** — 만든 것을 실제로 돌린다.
   코드가 컴파일되는 것과 의도대로 도는 것은 다른 문제다.

4. **커밋** — ⑤의 순서를 따른다.

5. **STATUS.md 갱신** — 아래 네 가지를 모두 적는다.
   - "끝난 것"에 이번 바퀴가 한 일과 커밋 해시
   - "다음에 할 것"에 다음 바퀴가 집을 작업 **하나**
     비워 두면 다음 바퀴는 이어받을 자리를 모른다. 반드시 채운다.
   - "결정과 근거"에 이번 바퀴에서 선택한 것과 그 이유
     왜 그렇게 정했는지가 남아야 다음 바퀴가 되돌리지 않는다.
   - 사람이 풀어야 할 것이 생겼으면 "막힌 것"에

6. **INBOX 정리** — INBOX 의 지시를 끝냈으면 **지우지 않는다.**
   "처리한 것"으로 옮기고 완료 표시와 처리 방법만 붙인다.

## ⑤ 커밋 순서 규칙

- **검사를 통과하면, 화면을 보기 "전에" 일단 커밋한다.**
  한 바퀴는 도중에 멈춘다 (턴 수 소진, 프로세스 종료, 정지 신호).
  멈춘 자리에 커밋이 없으면 그 바퀴의 작업은 통째로 사라진다.
  화면 확인에서 문제가 나오면 그때 고쳐서 다시 커밋하면 된다.

- **이번 바퀴가 직접 만들거나 고친 파일만 스테이징한다.**
  `git add -A` 와 `git add .` 를 쓰지 않는다. 경로를 하나씩 적는다.
  저장소에는 루프와 무관한 작업 중인 변경이 함께 있을 수 있고,
  한번 섞이면 어느 것이 루프의 결과인지 되돌릴 수 없다.

- **커밋 메시지에 무엇을 왜 했는지 적는다.** 다음 바퀴가 읽는 기록이다.

- **브랜치를 옮기지 않는다.** `loop/ui-improve` 에서 시작해 거기서 끝낸다.
  `checkout`, `switch`, `merge`, `rebase`, `reset --hard`, `push` 를 하지 않는다.

## ⑥ 검사와 QA

- **커밋 전에 아래를 돌린다. 하나라도 실패하면 커밋하지 않는다.**

  ```
  npm test
  node js/data/validate.js
  ```

  실패를 STATUS 의 "막힌 것"에 남기고 바퀴를 끝낸다.

- **화면이 있는 것을 만들면, 실행해서 스크린샷을 찍고 그 이미지를 직접 읽어라.**
  코드가 도는 것과 화면이 괜찮은 건 다른 문제다.
  글자가 잘렸는지, 겹쳤는지, 대비가 죽었는지, 빈 화면인지는 이미지를 봐야만 안다.
  **고치기 전과 후를 모두 찍어 비교한다.** 한 장만으로는 나아졌는지 알 수 없다.

- **같은 지적이 두 번 나오면 규칙으로 올린다.**
  ③의 표에 규칙과 "왜"를 함께 적는다.

- **기계가 잴 수 있는 규칙이면 검사로 만들어 둔다.**
  테스트든 린트 규칙이든, 다음 바퀴가 자동으로 걸리게 한다.
  한 번 겪은 고장을 두 번 겪지 않는다.
