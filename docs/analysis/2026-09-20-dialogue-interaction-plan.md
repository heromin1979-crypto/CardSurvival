# 직업별 대화·선택 확장 계획

상태: 현행 소스 감사 및 확장 설계 완료. 아래 신규 대화 콘텐츠는 아직 구현하지 않았다. 기존 직업 제작·수급 구현/검증 계획에 후속 작업으로 연결한다.

## 1. 현재 얼마나 있는가

`node tools/audit-dialogue-content.mjs`로 현재 병합 데이터를 집계했다. 재현 가능한 원본은 `progression-execution/dialogue-content-audit.json`이다. 숫자는 모든 직업·배타 분기를 합친 정의 수이며 한 회차 플레이 횟수가 아니다. 전수 도달률은 별도 플레이 검증 대상이다.

### 핵심 판단

대화 문안 자체보다 **주고받는 대화, 작은 결정, 결정 이후의 반응**이 부족하다. 모든 확인 창에 선택지를 추가하면 제작 흐름만 느려진다. 중요한 만남·운영 방식·관계 변화에 장면을 집중하고 반복 작업은 간결하게 유지한다.

`questScenes.createQuestScene()`은 `scene.speakerId` 또는 `objective.npcId`만 화자로 쓴다. 현재 명시 speakerId는0개, npcId 목표는3개다. 따라서 대부분 장면은 '생존 기록'으로 표시되며, NPC가 있는 것처럼 인물을 임의 배정하면 안 된다. 실제 대면, 무전, 독백을 구분하는 화자 메타데이터가 필요하다.

`NPCSystem.getDialogue()`는 같은 신뢰 구간에서 같은 인사/힌트를 선택한다. 직업·현재 공정·이전 선택·최근 사건을 조합하는 반응은 없다. `CareerProjectScene`의 투입/가동/운영 버튼은 기능적 상호작용이며 인물 간 이야기 선택으로 세지 않는다.

현재 작업 중인79개 프로젝트의 조작 화면과 환자 치료 단계도 기능적 대화 UI에 포함되지만 위 이야기 분기13개에 합산하지 않았다. 초기 진입·거래·치료·기여 선택이 같은 장면 시스템에 있어도 각각의 버튼 수를 콘텐츠 장면 수로 부풀리지 않는다.

## 2. 먼저 고칠 연결

1. `NPCStorySystem` 정비사 서사와 `npcMemories.js` 일부는 `craftCompleted`를 기다리지만 실제 CraftSystem은 `craftComplete`를 발행한다. 실제 완료 출력/대상을 검사하는 계약으로 맞춘다.
2. 학생 서사·기억·딜레마는 `exploreCompleted`를 기다리지만 현재 js에서 해당 이벤트 발행을 찾지 못했다. ExploreSystem의 **성공한 탐색 종료** 지점에 명시적 이벤트를 연결하고, 취소/전투 미해결/이동만으로 횟수가 오르지 않게 한다. 학생의 '5회 탐색'은 현재 이벤트1회 단계이므로 실제 누적5회 판정으로 바꾼다.
3. 개인 서사의 '함께 10일'은 현재 `_checkArcStep('day', GameState.time.day)`로 절대 날짜를 검사한다. 합류 이후 함께한 기간인지 설명만 바꿀 것인지 결정해야 한다. 본 계획은 동행 누적 기간으로 수정하고 구세이브는 알 수 없는 기간을 새로 보상하지 않는다.
4. `SecretEventModal`의 별도 큐를 DialogueScene 소유권에 연결한다. 기존 HiddenElementSystem 선택 판정·물품 비용·결과 확률은 보존한다. 기억·딜레마·환자 기여 선택도 장면 충돌/저장 복원을 함께 검사한다.

이 항목은 소스에서 발견한 연결 문제다. 수정 완료나 전체 재현 완료로 표시하지 않는다.

## 3. 직업별 초반→중반→후반

각 직업의 기존 분기/엔딩을 보존한다. 아래는 추가할 작은 선택이며 새로운 엔딩 여섯 세트를 만드는 계획이 아니다. 수량·TP·효율은 제작/지역 수급 검증 이후 정한다.

| 직업 | 초반의 대화 결정 | 중반 운영 결정 | 후반의 책임·인계 | 퀘스트 밖 재방문 대화 |
|---|---|---|---|---|
| 의사 | 환자에게 증상을 더 묻고 검사 / 보이는 위급 증상부터 안정화 | 간호사와 소독 소모품 비축 / 재사용 도구 멸균 설비 마련 | 공동 연구 데이터 공유 범위와 치료소 운영 인계 | 회복 상담, 이전 치료에 대한 감사·불안, 새로운 환자 소개 |
| 군인 | 무전 상대의 신원을 확인 / 긴급 위치 전달 후 현장 확인 | 구조 인원 수색 우선 / 보급 통로 확보 우선 | 구조망 담당자에게 통신·보급 업무 분담 | 순찰 보고, 약속했던 구조자 소식, 무전 상태 점검 |
| 소방관 | 진입 전 구조 상태 확인 / 우회 접근로와 장비 준비 | 가족 거처의 방수·난방 / 공동 급수·출입구 보강 | 대피소 주민에게 점검법 교육 / 부품 비축 후 인계 | 비 뒤 누수 상담, 구조된 주민의 도움, 장비 반환 |
| 셰프 | 식사 인원·상태를 묻고 메뉴 구성 / 확보한 식재료로 먼저 소량 제공 | 즉시 급식 / 보존식 비축; 재배 / 겨울 교환망 | 주방 운영법 전수 / 공동 식량창고 운영 | 기호·알레르기 등 게임 내 식사 요구, 지난 메뉴 반응, 식재료 교환 제안 |
| 기계공 | 고장 원인을 진단 / 회수 부품을 분해해 결함 확인 | 임시 수리로 한 설비 우선 / 추가 부품으로 안정 전원 구축 | 차량·공장·도시·헬기 기존 경로에서 유지보수와 운영 인계 | 소음·출력 이상 보고, 회수 부품 품질 상담, 수리했던 설비 후기 |
| 최형식 | 회수품을 선별해 교환 / 일부를 비축해 운반 설비 마련 | 한 번의 유리한 교환 / 반복 교환 약속과 재고 확보 | 타워 자치·공동 치료소·중개망의 분담 합의 | 시세·수요 변화, 지난 약속의 신뢰 반응, 신규 회수처 정보 |

동일 문제에도 전공의 접근법이 달라야 한다. 예를 들어 정수 설비 고장에 의사는 물 사용 우선순위, 기계공은 고장 진단, 최형식은 부품 교환, 소방관은 임시 급수 동선을 제안한다. 타 직업도 공통 방법으로 해결 가능하며 전공 선택은 비용 구조/정보/공정이 달라지는 대안이다.

## 4. 대사와 선택의 작성 규격

장면 하나는 **상황 발화 → 필요한 질문 → 2~3개의 실행 방법 → 즉시 반응 → 실제 플레이 → 재회 반응**을 기본 단위로 한다. 질문/떠나기는 실행 방법 수에 넣지 않는다. 한 화면은 선택4개 이내로 구성하고 추가 질문은 별도 목록으로 연다.

- [정보] 무엇이 부족한가: 현재 조건에 맞는 수급 지역·필요 공정을 알려준다. 반복해서 물어도 아이템/신뢰를 지급하지 않는다.
- [직업] 전문적으로 해결: 숙련·도구·시간을 검사하고 대체 공정을 연다. 버튼을 눌렀다는 이유만으로 치료/수리 완료로 처리하지 않는다.
- [도움] 함께 작업: 물품뿐 아니라 전달·설치·사용까지 요구한다.
- [거래] 부족분 교환: 실제 재고·비용·품목을 표시한다. 약속은 무한 무료 공급으로 바뀌지 않는다.
- [나중에] 준비 후 돌아오기: 긴급 사건 외에는 불필요한 신뢰 벌점을 주지 않는다. 보류와 영구 거절을 구분한다.

결과는 자원·TP·안전·관계·다음 수급 경로 중 최소 하나를 바꾸되, 모든 선택에 수치 보상이 필요하지는 않다. 관계 선택은 후속 대사와 행동 변화로 회수한다. 정보 없는 정답 맞히기, 선한 선택만 모든 면에서 이득인 구조, 표현만 다르고 결과가 같은 선택을 피한다.

대사 변형 우선순위는 사망/부재 등 불가능 상태 → 현재 사건/부족 자원 → 이전 선택에 대한 후속 반응 → 관계 변화 → 계절/생활 대사다. 조건마다 모든 문안을 곱하지 않고 기본문안 + 필요한 변형만 작성한다. 매 문장을 난수로 섞어 앞뒤 말투가 바뀌게 하지 않는다.

### 의사 장면 예시(신규 제안)

간호사: “소독한 거즈가 다음 환자까지는 버티겠어요. 그다음은 장담 못 해요.”

1. **[정보] 가장 많이 쓰는 곳이 어디죠?** → “상처 처치예요. 물과 천은 있는데 소독할 준비가 부족해요.” 현재 제작/공급처 힌트 표시.
2. **[직업] 재사용 도구를 멸균할 준비를 하죠.** → 설비와 실제 소모품 필요량 안내, 준비 목표 선택. 설치·작동을 완료해야 효과 발생.
3. **[도움] 오늘 쓸 소모품부터 마련하겠습니다.** → 단기 공급 경로 선택. 치료를 계속할 수 있으나 장기 설비는 별도 준비.
4. **[나중에] 재료를 확인하고 돌아올게요.** → 보류, 비용 없음.

멸균 설비 가동 후: “이제 도구를 버리지 않아도 되겠어요. 세척할 물은 계속 챙겨야 해요.”
소모품 공급 후: “오늘 환자는 받을 수 있겠어요. 다음번엔 비축분까지 생각해 봐요.”
자원 부족 재방문: “약속을 잊은 건 아니죠?” 같은 질책을 반복하지 않고 “천은 모였네요. 남은 소독 재료는 이쪽에서 구해볼 수 있어요.”처럼 실제 진척을 반영한다.

## 5. 콘텐츠 볼륨과 노출 빈도

초기 제작 범위는 직업당 핵심 대화6개(초·중·후반 각2) = 총36개, 퀘스트 외 생활/운영 주제4개 = 총24개로 잡는다. **총60개는 제작 목표이며 60개 전부 새로운 강제 팝업을 뜻하지 않는다.** 기존 시작/완료/비밀 이벤트를 재구성하는 것을 우선한다.

핵심36개는 각각 실행 대안2개 이상과 선택 후 반응을 갖춘다. 생활24개는 각각 상태 변형2개 이상을 작성한다. 이를 단순 대사 줄 수로 성과 측정하지 않고, 실행 결과 차이와 재방문 반영률로 확인한다. 첫 검증 묶음은 직업당 핵심1개+생활1개, 총12개로 제한해 재미와 노출 빈도를 먼저 확인한다.

주요 새 만남/위기/분기만 자동 장면으로 연다. 반복 운영과 일상 대화는 NPC 메뉴의 새 주제 표시로 사용자가 선택한다. 완료 보고 직후 새 목표가 열릴 때 두 확인 장면을 무조건 연달아 띄우지 않고 동일 맥락은 한 장면으로 묶을 수 있게 한다. 전투 중에는 큐에 두고 현재 장소·NPC 생존 상태를 표시 직전에 재검사한다.

## 6. 실제 구현 순서와 파일 경계

1. **발동 계약 복구:** NPCStorySystem, NPCRelationSystem, npcDilemmas/npcMemories, ExploreSystem. 재현 테스트 후 실제 이벤트·누적 횟수·동행 기간을 고친다.
2. **대화 데이터/상태:** 신규 `js/data/dialogueTopics.js`, `js/systems/DialogueTopicSystem.js`에 장면ID·노드·화자·조건·비용 설명·도메인 action·후속 반응을 정의한다. GameState에 방문노드/선택/대기/소비 이력 버전을 저장한다. 런타임 진행을 정의 객체에 쓰지 않는다.
3. **기존 UI 연결:** DialogueScene, NPCDialogueModal, questScenes에 질문/보류/다음 발화와 명시 화자를 연결한다. 첨부 이미지의 좌측 인물·우측 선택 구성을 유지한다. 현재 DESIGN.md/css/variables.css 재확인 후 구현한다.
4. **기존 기능 호출:** PatientTreatmentSystem, CareerProjectSystem, NPCSystem.executeTrade, ExploreSystem.useSupply를 통해 행동한다. UI가 재료·치료·프로젝트 플래그를 직접 바꾸지 않는다. 같은 행동을 퀘스트와 대화 양쪽에서 중복 보상하지 않는다.
5. **12개 시범 장면:** 각 직업의 현재 시작 지역·실제 NPC·프로젝트 ID와 일치시키고, 실제 수급 플레이 중 노출을 검증한다. 새로운 NPC를 가정하여 초상화만 붙이지 않는다.
6. **60개 확대 및 전수 검증:** 시범 피드백 이후36핵심/24생활 주제 매핑표를 확정한다. 번역키·빈 화자·끊어진 노드·도달 불가 조건을 데이터 검증에 포함한다.

검증 기준: 반복 클릭/재접속 비용1회, 저장 후 같은 선택 복원, 직업 조건과 공통 대안, 부족 재료의 정확한 안내, 사망/이탈 NPC 대체 경로, 보류 후 재진입, 대화 중 신규 퀘스트 큐, 844/1280/1920 UI, 기존 엔딩 분기 보존. 데이터 정의 수와 실제 플레이 장면 수를 따로 기록한다.

현재 제작·공급 작업4~6의 완료 조건을 이 신규 콘텐츠 수량 때문에 뒤로 늘리지 않는다. 기존 작업을 검증한 뒤 후속 대화 작업으로 실행한다. 기존 계획의 미완료 항목을 완료 처리하지 않는다.
