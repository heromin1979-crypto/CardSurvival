# Card Survival: Ruined City — AI 플레이테스트 운영·구축 가이드

> 상태: **도입 설계 및 운영 기준**  
> 기준일: 2026-08-28  
> 대상: 브라우저판을 우선으로 하는 Card Survival: Ruined City의 플레이 경험 검증

## 1. 목적과 적용 범위

이 문서는 AI가 실제 화면을 보며 플레이하는 테스트를 우리 게임에 도입하고 운영하는 기준이다. 단위·통합·시뮬레이션 테스트를 대체하지 않는다. 이 도구가 다루는 질문은 다음과 같다.

- 새 플레이어가 시작 직후 무엇을 이해하지 못하는가?
- 첫 5분 안에 이탈하게 되는 직접 원인은 무엇인가?
- 실제 조작과 화면 흐름에서 재현되는 결함은 무엇인가?
- 고정된 회귀 시나리오가 빌드마다 같은 결과를 내는가?

원문의 핵심 원칙인 **원본 비변경**, **실행별 격리**, **새 플레이어 관점의 블라인드 세션**, **증거가 남는 보고서**를 유지한다. 다만 이 프로젝트는 바닐라 JavaScript 기반의 브라우저 게임이며 Electron·Vite·Capacitor를 함께 사용하므로, 첫 구현 범위는 웹 빌드와 Windows에서의 화면 기반 실행으로 제한한다. LÖVE2D, iOS Simulator, 다른 게임 폴더 등록 기능은 이 프로젝트의 현재 구현 범위가 아니다.

## 2. 현재 검증 체계와 AI 플레이테스트의 역할

현재 저장소에는 이미 서로 다른 목적의 검증 경로가 있다. AI 플레이테스트 러너는 이 경로들의 상위 대체물이 아니라, 사람이 실제로 겪는 화면·조작·이해의 문제를 발견하는 보완 계층이다.

| 계층 | 실제 경로 | 답하는 질문 | AI 러너와의 관계 |
|---|---|---|---|
| 데이터 정합성 | `npm run check:data` → `js/data/validate.js` | 아이템·레시피·NPC·i18n 데이터가 유효한가 | 실행 전 게이트 |
| 단위·통합 | `npm test` → Vitest | 시스템 계약과 회귀가 깨지지 않았는가 | 실행 전/후 게이트 |
| 최소 부팅 | `node testdata/smoke-test.mjs` | GameState와 TP 진행이 가능한가 | 빠른 사전 확인 |
| 전투 화면 E2E | `npm run test:e2e:combat`, `npm run test:e2e:combat:full` | Playwright로 전투 화면과 상호작용이 정상인가 | 회귀 모드의 자동화 기반 |
| 밸런스 시뮬레이션 | `tools/sim/v2/` | 이상적 행동 모델에서의 생존·사망·행동 KPI는 어떤가 | 화면 플레이의 해석 보조 |
| AI 화면 플레이 | 이 문서의 제안 러너 | 실제 초보자 경험·이탈점·관찰 가능한 결함은 무엇인가 | 새로 도입할 계층 |

`tools/sim/v2/`는 화면을 보지 않는 결정론적 모델이다. 따라서 시뮬레이터의 생존율(K1), 사망일(K3), 사망 원인(K5), 행동 프로파일은 밸런스 가설을 세우는 자료이지, UI 이해도나 조작 흐름의 통과 증거가 아니다. 특히 현재 시뮬 AI는 중후반 전투·이동에 구조적으로 거의 도달하지 못한다는 한계가 문서화되어 있으므로, 해당 영역은 화면 기반 세션으로 별도 확인한다.

## 3. 운영 원칙

### 3.1 원본 게임은 읽기 전용 입력이다

일반 플레이테스트는 원본 소스·작업 트리·개발자 저장 데이터를 수정하지 않는다. 실행 전 허용된 빌드 명령으로 웹 산출물을 만들고, 그 **산출물만** 실행별 디렉터리로 복사해 구동한다. Electron 검증도 같은 원칙으로, 패키징 결과를 복사해 실행한다.

AI가 세션 중 화면에 보이는 요소를 조작하는 것은 허용하지만, 소스 수정·DevTools·콘솔·DOM 탐색·로컬 저장소 직접 편집은 허용하지 않는다. 문제가 발견되어도 AI는 수정하지 않고 증거와 재현 절차만 보고한다.

### 3.2 실행 단위가 독립적이어야 한다

각 실행은 새로운 브라우저 프로필, 새로운 저장 데이터, 새 로그 폴더, 새 스크린샷/영상 경로를 사용한다. 이전 런의 진행도·쿠키·캐시·보고서가 다음 런의 판단을 오염시키면 안 된다. 시드가 필요한 회귀는 등록된 시드를 명시하고, 자연 탐색은 새 시드 또는 새 저장으로 시작한다.

### 3.3 블라인드 모드는 실제로 눈가림한다

`first_time_player`와 `hook` 모드에서 AI 워커에게 제공할 것은 화면 좌표 기반의 `playtest` 도구와 최소 실행 규칙뿐이다. 다음 정보는 제공하지 않는다.

- `js/`, `css/`, `assets/`의 원본 소스와 개발 문서
- 이전 실행 보고서, 시뮬레이션 결과, 알려진 버그 목록
- 브라우저 DOM, 콘솔, 네트워크/저장소 상태, 런타임 객체
- 게임 규칙의 정답, 숨겨진 해금 조건, 의도된 공략

`qa`에서만 사전에 등록한 제한 경로와 런타임 로그 사본을 `qa-context`에 제공할 수 있다. 이 경우에도 원본에는 쓰기 권한을 주지 않는다.

### 3.4 실패는 증거로 분류한다

"재미없다"나 "이상하다"만으로 결론 내리지 않는다. 모든 문제는 관찰 시점, 화면 증거, 실제 입력, 기대와 실제 결과, 재현성, 영향도를 가진다. 추정 원인은 `가설`로 명확히 표시하며, 원인이 확인된 것처럼 쓰지 않는다.

## 4. 권장 아키텍처

첫 구현은 별도 로컬 도구 `tools/ai-playtest-runner/`로 둔다. 게임의 프로덕션 소스와 테스트 도구의 책임을 섞지 않기 위함이다. 생성되는 런 데이터는 Git 추적에서 제외한다.

```text
개발 작업 트리 (읽기 전용 입력)
  ├─ npm run build:web
  ├─ check:data / Vitest / 기존 E2E
  └─ dist-web/ 또는 승인된 웹 산출물
                │ 복사
                ▼
.ai-playtest/runs/<run-id>/                 # 실행별 격리 영역
  ├─ game/                                  # 복사된 웹 빌드
  ├─ browser-profile/                       # 새 Chromium 프로필
  ├─ evidence/                              # screenshot, video, trace
  ├─ logs/                                  # 서버·워커 로그
  ├─ qa-context/                            # qa 모드에서만 제한 복사
  ├─ run.json                               # 입력·환경·시드·상태
  └─ report.json + report.md                # 정형 결과
                │ 화면 좌표만 노출
                ▼
AI 워커 (별도 임시 작업공간)
  └─ screenshot / click / drag / key / wait / checkpoint
```

### 4.1 실행 수명주기

1. **사전 게이트**: `npm run check:data`, 관련 Vitest, 필요한 Playwright E2E, `npm run build:web`를 실행한다. 실패하면 플레이 세션을 시작하지 않고 해당 실패를 선행 결함으로 기록한다.
2. **준비**: 현재 Git revision, 빌드 명령, 실행 모드, 페르소나, 해상도, 언어, 시드, 허용 시간, 회귀 케이스 ID를 `run.json`에 기록한다.
3. **격리 복사**: 빌드 산출물을 런 폴더의 `game/`으로 복사한다. 원본 프로젝트나 개발 서버를 AI가 직접 열지 않는다.
4. **실행**: 루프백(`127.0.0.1`) 정적 서버와 신규 Chromium 사용자 데이터 디렉터리로 게임을 연다.
5. **플레이**: 워커는 화면 캡처와 좌표 기반 입력만 사용한다. 의미 있는 상태 변화마다 체크포인트를 남긴다.
6. **수집**: 종료·오류·시간 제한 시 증거를 고정하고, 블라인드 모드에서는 소스 없이 보고서를 만든다.
7. **정리**: 게임/브라우저/서버만 안전하게 종료한다. 원본 산출물과 다른 런은 건드리지 않는다. 보존 기간이 지난 런 삭제는 명시적 정책 또는 사용자 조작으로만 한다.

### 4.2 실제 도입 순서

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 1 | 웹 빌드 격리·신규 브라우저 프로필·수동 실행 | 원본 저장/소스가 바뀌지 않고 격리된 게임이 열린다 |
| 2 | 화면 캡처·좌표 입력·체크포인트·정형 보고서 | `first_time_player`, `hook` 1회씩 증거와 함께 종료된다 |
| 3 | 회귀 케이스 레지스트리·Playwright 아티팩트 연계 | 동일 시드/절차를 재실행해 비교할 수 있다 |
| 4 | 제한된 QA 컨텍스트·큐·예약 실행 | 실패 시 안전한 중지와 원인 가설이 남는다 |
| 5 | Electron/Android 어댑터 | 웹 경로의 격리·증거·권한 기준을 충족한 뒤 추가한다 |

## 5. 모드와 게임별 관찰 기준

### `first_time_player` — 첫 진입 경험

목표는 잘하는 플레이가 아니라, 도움 없이 기본 생존 루프를 이해할 수 있는지 확인하는 것이다. 새 저장으로 시작하여 캐릭터 선택, 보드 읽기, 카드 선택/드래그, 탐색·소비·제작·휴식, 시간(TP) 진행, 첫 위험/전투 진입을 자연스럽게 시도한다.

필수 관찰 항목은 다음과 같다.

- 시작 직후 목표와 다음 행동 후보가 화면만으로 드러나는가
- 허기·갈증·피로·사기·오염 등 HUD의 긴급도가 구분되는가
- 카드의 획득·소비·제작·장착 가능 여부와 실패 이유가 이해되는가
- 구 이동, 탐색 결과, 퀘스트 진행, 야간 전환의 인과가 보이는가
- 전투 진입 후 행동 순서·대상·위협 의도가 파악되는가

### `hook` — 5분 이탈점

최대 5분 동안 일반 사용자의 속도로 플레이한다. 막히거나 흥미가 사라지는 첫 지점을 기록하되, AI가 억지로 정답을 찾으며 계속 진행하지 않는다. 결과는 이탈 시점, 직접 원인, 화면 신호의 부재/혼란, 계속했을 가능성을 높일 최소 변경 제안으로 작성한다.

### `qa` — 화면 재현 후 제한된 원인 가설

등록된 버그 또는 새 관찰을 먼저 화면으로 재현한다. 재현 뒤에만 `qa.sourcePaths`에 등록된 파일 사본과 해당 런의 서버/브라우저 로그를 읽어 가설을 만든다. 가설에는 확인 대상 함수·데이터 키·추가 검증을 적되, 플레이테스트 워커가 원본을 수정하지는 않는다.

### `regression` — 등록 시나리오만 검증

각 케이스는 시작 조건, 입력 순서, 관찰 가능한 통과 조건, 증거 체크포인트를 갖는다. 전투 UI는 이미 Playwright E2E가 있으므로, AI 회귀는 기존 자동 테스트가 닿지 않는 이해도·자연 조작·시각적 피드백을 보완하는 케이스부터 등록한다.

### `simulation` — 화면 플레이와 분리한 보조 측정

`node tools/sim/v2/run_baseline.mjs`는 6직업 × 100회 baseline과 K1/K3/K5, 자원·행동 프로파일을 생성한다. 이 결과는 보고서의 "밸런스 정황"에 첨부할 수 있지만, 시뮬레이터가 대리하는 행동과 실제 화면 세션을 같은 표본으로 합산하거나 통과 판정에 혼용하지 않는다.

## 6. 실행 설정 계약

모든 실제 런은 아래처럼 버전 관리 가능한 설정에서 시작한다. 경로는 프로젝트 루트 기준 상대 경로만 사용하고, 사용자명·드라이브 문자가 포함된 절대 경로를 예시나 기본값에 넣지 않는다.

```json
{
  "schemaVersion": 1,
  "projectId": "card-survival-ruined-city",
  "adapter": "web",
  "build": {
    "command": ["npm", "run", "build:web"],
    "outputDir": "dist-web"
  },
  "launch": {
    "entry": "index.html",
    "host": "127.0.0.1",
    "viewport": { "width": 1920, "height": 1080 },
    "locale": "ko-KR"
  },
  "isolation": {
    "freshProfile": true,
    "freshSave": true,
    "blockSourceInBlindModes": true
  },
  "qa": {
    "sourcePaths": ["js/core", "js/systems", "js/data"],
    "runtimeLogPaths": []
  }
}
```

`build.command`는 등록된 이 프로젝트의 설정에서만 실행한다. GUI나 HTTP 요청이 임의 명령을 전달하게 해서는 안 된다. `qa.sourcePaths`도 기본적으로 비워 두고, 재현에 필요한 범위만 케이스별로 허용한다.

## 7. 제어·권한·보안 경계

### 7.1 웹 어댑터

웹 어댑터는 Chromium을 새 프로필로 실행하고 스크린샷, 클릭, 드래그, 키 입력, 대기, 체크포인트만 워커에 제공한다. DOM selector, `evaluate`, 개발자 도구 프로토콜, console 로그는 블라인드 워커의 도구 목록에 포함하지 않는다. 브라우저는 창 모드, 지정 viewport, `ko-KR`로 실행한다.

Playwright는 이미 개발 E2E에서 사용하지만, 그 Playwright 권한을 블라인드 AI에 그대로 제공하지 않는다. E2E는 코드가 작성한 명시적 selector 검증이고, 블라인드 플레이는 화면을 보고 판단하는 독립된 실험이다.

### 7.2 Electron과 Android

Electron 및 Android는 1단계 웹 어댑터가 안정된 뒤에만 다룬다. Electron은 패키징 산출물 복사본을 창 모드로 실행하고, Android는 사용자가 명시적으로 선택한 에뮬레이터/연결 기기에서만 실행한다. 모바일 기기 접근, 화면 녹화, 입력 제어가 필요한 경우 해당 플랫폼의 사용자 동의를 별도로 확인한다. 웹 런에 Android·화면 제어·불필요한 권한을 요청해서는 안 된다.

### 7.3 로컬 실행 원칙

- 서버는 `127.0.0.1`에만 바인딩한다.
- 런의 기록은 `.ai-playtest/` 아래에 두고 `.gitignore`로 제외한다.
- 인증 정보, 실제 사용자 저장 데이터, 외부 서비스 토큰을 런에 복사하지 않는다.
- 중지 요청이 오면 현재 입력을 멈추고, 자식 프로세스만 종료한 뒤 증거를 보존한다.
- 권한 또는 필수 런타임이 없으면 `unsupported` 또는 구체적 진단을 반환한다. 우회·관리자 권한 요청·시스템 설정 변경을 시도하지 않는다.

## 8. 페르소나와 프로토콜

한 번의 AI 플레이를 일반화하지 않기 위해 세션마다 행동 성향을 기록한다. 페르소나는 규칙 정답을 공유하지 않으며 입력 템포와 탐색 성향만 바꾼다.

| 페르소나 | 행동 원칙 | 특히 잘 드러나는 문제 |
|---|---|---|
| `neutral` | 화면에서 가장 자연스러운 다음 행동을 택함 | 기본 이해도, 전체 흐름 |
| `cautious` | 위험 신호를 우선 피하고 설명을 찾음 | 경고·실패 피드백, 안전한 학습 경로 |
| `impatient` | 빠르게 진행하며 긴 설명을 건너뜀 | 첫 5분 이탈, 마찰, 클릭 수 |
| `explorer` | 카드·패널·구역을 폭넓게 살핌 | 발견성, 잠긴 콘텐츠의 안내 |
| `casual` | 장르 지식 없이 단순한 추측으로 조작 | 온보딩, 용어, HUD 가독성 |

프로토콜은 모드별로 시작 조건, 최대 시간, 체크포인트, 종료 조건, 금지 행동을 고정한다. 예를 들어 `hook`은 5분 제한과 첫 직접 이탈 원인 기록을 강제하고, `regression`은 등록된 입력 외의 탐색을 금지한다.

## 9. 체크포인트와 증거

체크포인트는 화면 이미지 한 장만 의미하지 않는다. 다음 데이터를 함께 저장한다.

| 필드 | 내용 |
|---|---|
| `at` | 경과 시간과 게임 내 day/TP(화면에서 관찰 가능할 때만) |
| `label` | 예: `onboarding`, `first-craft`, `nightfall`, `combat-entry`, `exit-point` |
| `action` | 직전의 실제 입력과 대상 |
| `observation` | 화면에서 확인한 사실 |
| `expectation` | 플레이어가 합리적으로 기대했을 결과 |
| `result` | 실제로 발생한 결과 |
| `evidence` | screenshot/video/trace의 상대 경로 |

게임의 보드·HUD·전투 화면은 해상도와 스케일에 민감하므로, viewport와 브라우저 배율도 각 런에 기록한다. 기존 전투 E2E가 사용하는 1920×1080 및 1280×820 사례를 참고하되, AI 런의 기준 해상도는 설정에 명시한다.

## 10. 보고서 계약

각 런은 `report.json`(기계 비교용)과 `report.md`(검토용)를 만든다. 보고서 최상단에는 통과/실패 단정이 아니라 세션의 성격과 제한을 먼저 적는다.

```json
{
  "schemaVersion": 1,
  "runId": "20260828T120000Z-hook-casual-001",
  "mode": "hook",
  "persona": "casual",
  "status": "completed",
  "build": { "gitRevision": "<commit>", "command": "npm run build:web" },
  "environment": { "adapter": "web", "viewport": "1920x1080", "locale": "ko-KR" },
  "isolation": { "freshProfile": true, "freshSave": true, "sourceVisibleToWorker": false },
  "summary": {
    "outcome": "첫 탐색 이후 다음 목표를 이해하지 못해 중단",
    "confidence": "medium"
  },
  "findings": [
    {
      "id": "PT-001",
      "severity": "high",
      "reproducibility": "3/3",
      "observation": "...",
      "expected": "...",
      "actual": "...",
      "hypothesis": null,
      "evidence": ["evidence/checkpoint-03.png"]
    }
  ],
  "checkpoints": [],
  "artifacts": []
}
```

`severity`는 플레이 불가/데이터 손실 위험인 `blocker`, 진행을 반복적으로 막는 `high`, 혼란·오해를 만드는 `medium`, 개선 후보인 `low`로 제한한다. `qa`의 `hypothesis`는 재현과 코드·로그 확인을 모두 마친 경우에만 채우며, 그렇지 않으면 `null`로 둔다.

보고서 검토 시에는 다음을 분리한다.

1. **관찰 사실**: 어떤 화면에서 어떤 입력 뒤 무엇이 보였는가.
2. **플레이어 해석**: 왜 그 화면을 그렇게 이해했는가.
3. **원인 가설**: `qa` 컨텍스트로 뒷받침된 경우에만 제시한다.
4. **후속 검증**: 데이터 검증, Vitest, E2E, 수동 재현, 시뮬 재측정 중 무엇이 필요한가.

## 11. 회귀 케이스 레지스트리

회귀 케이스는 코드 파일명이 아니라 플레이어가 볼 수 있는 계약으로 등록한다. 예시는 다음과 같다.

| ID | 시작 조건 | 수행 | 관찰 가능한 통과 조건 | 기존 보완 경로 |
|---|---|---|---|---|
| `PT-ONB-001` | 새 저장·기본 캐릭터 | 첫 화면에서 1분 자연 탐색 | 생존 수치와 첫 행동 후보를 화면만으로 설명 가능 | smoke + 수동 확인 |
| `PT-CRAFT-001` | 제작 재료 보유 세이브 | 레시피 선택·제작 시도 | 성공/불가 사유와 결과 카드가 명확 | 관련 Vitest + `check:data` |
| `PT-COMBAT-001` | 전투 진입 가능한 저장 | 대상 선택·행동 실행 | 선택 상태, 적 의도, 결과가 시각적으로 일관 | `test:e2e:combat:full` |
| `PT-NIGHT-001` | 야간 전환 직전 저장 | TP 진행 | 야간 전환과 위험/선택 변화가 인지 가능 | Night 관련 단위·통합 테스트 |

처음에는 저장 상태 재현이 어려운 복잡한 케이스를 대량 등록하지 않는다. 새 저장에서 재현 가능한 온보딩과 `combat-test.html` 기반의 전투 화면부터 시작하고, 이후에 승인된 fixture 세이브 형식을 추가한다.

## 13. 현재 상태와 도입 완료 기준

이 저장소에는 Vitest, Playwright 기반 전투 E2E, `testdata/smoke-test.mjs`, `tools/sim/v2/`가 존재한다. 반면 실행별 게임 복사·별도 AI 워커·블라인드 좌표 도구·정형 `report.json`·페르소나 큐는 아직 이 문서가 정의하는 **도입 대상**이다. 따라서 이 문서는 현재 기능 목록이 아니라, 구현과 운영의 승인 기준이다.

웹 1단계는 아래 조건을 모두 만족할 때 도입 완료로 본다.

1. `npm run build:web` 산출물을 새 런 폴더에서 실행하고 원본을 수정하지 않는다.
2. 각 런은 독립 Chromium 프로필과 새 저장으로 시작한다.
3. 블라인드 워커는 화면 캡처와 좌표 입력만 사용하며 소스·DOM·콘솔을 읽지 못한다.
4. `first_time_player`, `hook`, `qa`, `regression`이 서로 다른 프로토콜과 보고서 필드를 사용한다.
5. 실패·중지·권한 부족이 구체적인 진단을 남기고 원본·다른 런을 훼손하지 않는다.
6. 보고서의 finding이 증거, 재현 정보, 영향도, 후속 검증 경로를 가진다.

## 15. 지금 바로 하는 플레이테스트

웹 MVP에는 자동 AI 워커가 구현되어 있다. 먼저 `doctor`로 Codex CLI·Playwright Chromium·웹 빌드 상태를 확인하고, `first_time_player` 또는 `hook` 모드로 실행한다. `qa`, `regression`, Electron, Android, iOS는 아직 지원하지 않으므로 수동 절차와 기존 자동 테스트를 사용한다. 아래 명령은 프로젝트 루트에서 실행한다.

### 15.1 준비와 사전 검증

처음 실행하는 환경이라면 의존성을 설치한다.

```powershell
npm install
```

그 다음 데이터와 최소 부팅을 먼저 확인한다.

```powershell
npm run check:data
node testdata/smoke-test.mjs
```

변경 범위가 넓거나 전투를 건드렸다면 다음까지 실행한다.

```powershell
npm test
npm run test:e2e:combat:full
```

명령 중 하나라도 실패하면 수동 플레이 결과와 섞어 판단하지 않는다. 먼저 실패한 테스트의 원인을 분리해 해결하거나, 플레이 노트에 사전 검증 실패로 기록한다.

### 15.2 자동 AI 화면 플레이를 실행한다

~~~powershell
# Codex CLI, Playwright Chromium, 기존 웹 빌드 상태 점검
npm run playtest:doctor

# 웹 빌드를 격리 런으로만 준비
npm run playtest:prepare -- --mode hook

# AI가 새 브라우저 프로필에서 화면 전용 도구로 플레이
npm run playtest -- --mode first_time_player --persona casual
~~~

`playtest`는 먼저 `npm run build:web`를 실행하고, 산출물만 `.ai-playtest/runs/<run-id>/game/`으로 복사한다. 각 런에는 신규 Chromium 프로필, 스크린샷, 체크포인트, `report.json`, `report.md`가 생성된다. `doctor`가 실패하면 부족한 항목을 해결한 뒤 다시 실행하며, 원본 소스나 저장 데이터를 AI에 제공하지 않는다.

이미 생성한 빌드 산출물의 격리 동작만 확인할 때는 `--skip-build`를 덧붙일 수 있다.

~~~powershell
npm run playtest:prepare -- --mode hook --skip-build
~~~

### 15.3 브라우저에서 새 게임을 수동으로 플레이한다

```powershell
npm run dev:web -- --host 127.0.0.1
```

Vite가 출력한 로컬 주소(일반적으로 `http://127.0.0.1:5173`)를 브라우저에서 연다. 기존 진행이 판단을 오염시킬 수 있으므로 브라우저의 시크릿 창 또는 별도 브라우저 프로필을 사용하고, 게임에서 새 저장으로 시작한다.

첫 세션은 15~30분 동안 아래 순서로 플레이하면 충분하다.

1. 캐릭터 선택 뒤 화면만 보고 생존 수치와 첫 행동을 이해할 수 있는지 기록한다.
2. 탐색, 소비, 제작, 휴식, TP 진행을 각각 한 번 이상 시도한다.
3. 야간 전환, 퀘스트 변화, 구 이동 또는 전투 진입 중 도달 가능한 흐름을 기록한다.
4. 막히거나 다음 행동을 알 수 없었던 최초 시점에 스크린샷을 찍고, 무엇을 기대했는지와 실제 결과를 한 줄씩 적는다.

개발 서버는 테스트를 마치면 실행한 터미널에서 `Ctrl+C`로 종료한다.

### 15.4 Electron 빌드로 확인한다

브라우저판과 데스크톱 패키징의 차이를 확인해야 한다면 다음을 사용한다.

```powershell
npm run start
```

변경 사항을 실제 배포 형태로 확인해야 할 때만 패키징을 실행한다.

```powershell
npm run build
```

패키징은 시간이 더 걸리며 `dist/` 산출물을 만든다. 일반 게임 흐름 검증은 먼저 브라우저판에서 수행하고, 창 동작·패키징·파일 경로 관련 문제만 Electron으로 재확인한다.

### 15.5 밸런스 수치도 함께 확인한다

화면 플레이에서 생존 난이도나 특정 직업의 체감 문제가 보이면, 화면 결과와 별도로 시뮬레이션을 실행한다.

```powershell
node tools/sim/v2/run_baseline.mjs
```

이 명령은 6직업 × 100회 결과를 `simulation-data/baselines/raw/`에 저장한다. 화면 플레이의 경험적 관찰과 시뮬레이션의 수치를 같은 결론으로 단정하지 말고, 예를 들어 “초보 플레이에서 음식 경로가 불명확했다”와 “시뮬레이션에서도 아사 비중이 높다”처럼 서로를 뒷받침하는 정황으로 함께 기록한다.

세션마다 아래 양식으로 남기면 AI 러너가 도입된 뒤에도 같은 형식으로 비교할 수 있다.
